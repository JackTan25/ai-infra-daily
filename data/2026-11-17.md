### [1] [Performance-Portable Exact Gaussian Process Regression in Python via SYCL and oneMath](https://arxiv.org/abs/2611.17565)
*Alexander Strack,Marcel Graf,Alexander Van Craen,Dirk Pflüger*

Main category: cs.DC

TL;DR: GPRat 在 HPX 异步多任务运行时之上引入基于 UXL Foundation oneMath（SYCL）的混合后端，使单一 SYCL 代码库可跨 NVIDIA/AMD/Intel GPU 运行；在 A30 上逼近原生 CUDA（差距 3%），在 A30 与 MI210 上分别比 GPflow/GPyTorch 快至 1.75x/2.17x 与 1.79x/4.62x。


<details>
  <summary>Details</summary>
Motivation: 多厂商 GPU 环境迫使开发者在"可移植代码"与"原生性能"之间二选一：CUDA 性能好但锁定 NVIDIA，纯 SYCL 可移植但往往因 BLAS 后端选择不当而损失性能。作者希望验证：通过 oneMath 将算子派发到厂商原生 BLAS，能否在不写厂商专用代码的前提下同时获得可移植性与接近原生的性能，并把 GPRat 的精确高斯过程回归扩展到 AMD、Intel GPU。

Method: 在 GPRat（开源 Python 精确 GPR 库）中新增 oneMath 后端：保留 HPX 异步多任务运行时与分块（tiled）算法负责任务并行与块级调度，将计算内核改写为 SYCL，并通过 UXL Foundation oneMath 接口在运行时派发到 cuBLAS / rocBLAS / oneMKL 等厂商原生 BLAS；形成 HPX（任务级异步并行）+ SYCL/oneMath（设备内核与 BLAS 派发）的混合设计。评测对象为 A30（FP64）、MI210（FP64）与消费级 Arc B580（FP64 较弱），对比 GPRat 的 CUDA/CPU 后端及 GPflow、GPyTorch。

### [2] [TailGuard-GDS: Tail-Safe Control of GPU Storage Data Movement](https://arxiv.org/abs/2611.17824)
*Jiaqi Liu,Fan Yang,Xiaohang Shi,Xianzhe Zhang,Tao Jiang,Guojun Yuan,Zhan Wang,Guangming Tan*

Main category: cs.DC

TL;DR: TailGuard-GDS 是一个面向 GPU I/O 的运行时，按应用阶段在语义等价的多种数据传输路径（host staging / GDS / 不同请求形状与放置）之间动态选择，以最小化 GPU 可见的尾延迟。在 8×H100 上集成 PyTorch FSDP 与 DeepSpeed ZeRO-3，FSDP step p95 降低 18.4%、GPU 空闲 p95 降低 25.3%（对比最强固定路径）；ZeRO-3 五类负载 step p95 比固定 host staging 降 7.9–24.6%、比固定 GDS 降 28.4–42.6%，对比调优后的 DeepSpeed AIO 降 5.6% 并提升约 6.1% 吞吐。


<details>
  <summary>Details</summary>
Motivation: AI runtime 在关键路径上频繁在 NVMe 与 GPU 显存之间搬运状态（checkpoint、offload、参数/优化器状态换入换出）。GPUDirect Storage（GDS）虽省去 host staging，但作者在 8×H100 上的实测表明：对语义等价的 GPU buffer 操作，GDS 并非一致的尾延迟最优——最优路径随操作类型、请求大小、并发度、数据放置与资源竞争而变化，且带宽最优与尾延迟最优常常不一致。现有框架只规定"搬什么、何时搬"（phase semantics），GPU I/O 栈只暴露"怎么搬"的机制，二者未结合，因此缺少一个基于实测尾行为来选择交付方案的决策层。

Method: TailGuard-GDS 以"应用阶段（phase）"为决策粒度，为每个阶段选择语义等价的数据交付计划：1) 剖面化（profiling）由后端（host staging vs GDS）、请求形状（size/chunk/批合并）、数据放置（pinning、NUMA/PCIe 拓扑、buffer 位置）构成的计划空间；2) 在阶段约束下以 GPU 可见尾延迟（p95/p99）为目标做最小化选择，而非单纯带宽；3) 条件变化时重新评估并迁移决策；4) 通过资源复用（复用已建立的 buffer/描述符/注册状态）将策略查找与路径切换开销压到微秒级，避免切换本身成为新开销。与 PyTorch FSDP、DeepSpeed ZeRO-3 集成。

Conclusion: 该工作的系统贡献在于把 GPU I/O 交付路径选择从"静态机制选择"提升为"阶段感知 + 尾延迟驱动的运行时策略"，并证明在真实大规模训练栈中路径选择差异是可观的（数十个百分点量级的 p95 差）。工程影响： (1) 对 FSDP/ZeRO 类 offload 与 checkpointing 系统，应把 I/O 路径当作可调度资源、以 p95 而非均值/带宽为优化目标；(2) 需要框架与 I/O 栈之间的 phase 语义接口（阶段标注 + 可切换交付原语），否则优化空间无法暴露；(3) 切换开销（微秒级）是可行性的关键约束，注册/复用机制必不可少；(4) 启示是"GDS 一律更优"是错误假设，默认路径规划需按大小/并发/拓扑分档。局限：收益为单集群 8×H100 规模、依赖离线/在线 profiling 成本与对 phase 边界的准确识别，跨节点存储（网络文件系统、分布式 checkpoint）与异构拓扑下的可迁移性仍需验证。

Abstract: AI runtimes move state between NVMe storage and GPU memory on critical paths. GPUDirect Storage (GDS) removes host staging, yet our eight-H100 measurements show it is not consistently tail-optimal for semantically identical GPU-buffer operations. The preferred path varies with operation, request size, concurrency, placement, and resource contention; bandwidth and tail-latency winners can disagree. Frameworks specify what moves and when, while GPU I/O stacks expose mechanisms; neither combines phase semantics with measured tail behavior to choose a delivery plan.

It profiles plans varying backend, request shape, and placement, minimizes GPU-visible tail latency under phase constraints, and revisits decisions as conditions change. Resource reuse keeps policy lookup and switching at microsecond-scale overhead.
  Integrated with PyTorch FSDP and DeepSpeed ZeRO-3, TailGuard reduces FSDP step p95 by 18.4% and GPU-idle p95 by 25.3% versus the strongest fixed path. Across five eight-GPU ZeRO-3 workloads, step p95 falls 7.9-24.6% versus fixed host staging and 28.4-42.6% versus fixed GDS. Against tuned DeepSpeed AIO, TailGuard reduces step p95 by 5.6% and raises estimated throughput by 6.1%.

### [5] [Callo: Serving Cache-Miss Requests with Speculative Decoding on Invalidated KV under Prefill-Decode Disaggregation](https://arxiv.org/abs/2611.18459)

<details>
  <summary>Details</summary>

We present Callo, a disaggregated serving system that leverages invalidated KV for speculative drafts to reduce this latency, while verifying drafts against the exact KV after prefill before committing tokens. Callo makes effective use of decode resources by scheduling speculations during periods of underutilization and preempting speculations when drafts are likely to not be accepted. We evaluated Callo on a two-GPU testbed using SWE-agent sessions across three model families, observing all-request speedups of 1.05-1.19x over vLLM at moderate load. We demonstrate that these gains are also realized at scale through cluster-level simulations driven by real-world traces.
