### [1] [NUMA-Torch: Compiler-Driven NUMA-Aware LLM Prefill on Multi-Socket CPUs](https://arxiv.org/abs/2611.07105)
*Thisara Rathnayaka Weerakoon,Ishan Dewpura,Niman Ransindu,Shavin Anjitha,Tharindu R. Patabandi,Sanath Jayasena*

Main category: cs.DC

TL;DR: 该论文把 TorchInductor 改造成 NUMA 感知编译器，将每个 NUMA socket 视为一个独立的 tensor-parallel 分区（NUMA-TP），透明地按 socket 切分权重并用 CPU 亲和性把线程池与内存分配绑定在本 socket，从而消除跨 socket 访存，在多路 CPU 上大幅提升 LLM prefill 吞吐。


<details>
  <summary>Details</summary>
Motivation: 大模型权重放不进片上 cache，多 socket CPU 上的 prefill 已从算力受限转为可持续 DRAM 带宽受限。而 TorchInductor 默认分配权重时完全不考虑 NUMA 拓扑，不区分 memory bank 与计算核的亲和性，导致相当比例的权重访问穿越 inter-socket 互连（如 UPI/QPI），每个 socket 的有效带宽被严重压缩。这是一个纯软件/调度层面的、无需改硬件的性能损失。

Method: 编译器级改造而非运行时库改造：在 TorchInductor 中引入 NUMA-aware Tensor Parallelism。核心做法有三点：(1) 以 NUMA socket 为并行粒度，把权重按输出/输入维度切分到各 socket 的本地内存；(2) 用 CPU affinity 把每个 socket 的线程池严格绑定到该 socket 的核上，使 kernel 只在本 socket 计算本地分片；(3) 让内存分配（页的 first-touch / 绑核分配）与线程池保持一致，保证数据局部性。由于恰好是 tensor-parallel 语义，跨 socket 只需在需要时做一次聚合（如 all-reduce/reduce-scatter 语义的归约），把跨 socket 通信从"每次权重读取都跨 socket"降为"每个 TP 边界只同步一次中间激活"。

Result: 在双路 Haswell 上 prefill 最高 2.63x，双路 Cascade Lake 最高 1.87x，四路 Haswell-EX 最高 2.27x。测试负载覆盖 GPT-2 (117M/345M/762M)、BERT (Small/Large) 的 MHA+MLP，以及 Gemma 3 270M 的 MQA + GeGLU-gated MLP，说明方法对标准注意力与门控 MLP 两类结构都成立。四路平台加速比低于双路，提示拓扑越复杂、socket 间跳数与归约开销越显著。

Conclusion: 结论是：对 LLM prefill 这类带宽受限负载，"NUMA 感知的权重分片 + 绑核调度"应当作为编译器的默认优化而非用户手动调优，其收益与 CPU 代际、socket 数量强相关。论文也隐含暴露了边界——只针对 prefill（compute-bound 的 decode 阶段收益会不同）、只针对多 socket 且权重放不进 LLC 的场景。

Abstract: For sufficiently large transformer-based Large Language Models (LLMs), whose parameters cannot be retained in on-chip caches, prefill throughput on multi-socket CPUs is often limited by sustainable DRAM bandwidth rather than peak floating-point throughput. In the standard PyTorch compilation (i.e., TorchInductor) path, model weights are allocated without considering the Non-Uniform Memory Access (NUMA) topology: specifically, the affinity between memory banks and compute cores is disregarded. This causes a substantial fraction of weight accesses to traverse the inter-socket interconnect, severely degrading the effective memory bandwidth available to each socket. We address this bottleneck through a compiler-level solution that makes TorchInductor NUMA-aware. Treating each NUMA socket as an independent tensor-parallel partition, we introduce NUMA-aware Tensor Parallelism (NUMA-TP). This approach transparently shards weights across sockets and schedules compute kernels such that thread pools and memory allocations remain strictly local to their respective sockets using CPU affinity. We evaluate the approach on GPT-2 (117M, 345M, 762M) and BERT (Small, Large), which exercise standard multi-head attention and MLP, as well as Gemma 3 270M, which combines Multi-Query Attention with a GeGLU-gated MLP. By strictly enforcing data locality, our approach successfully mitigates cross-socket traffic, achieving prefill speedups of up to 2.63x on a dual-socket Haswell platform, up to 1.87x on a dual-socket Cascade Lake platform, and up to 2.27x on a four-socket Haswell-EX platform.

### [2] [KOSMOS: Self-scheduling Persistent Kernels for Communication-Compute Overlap](https://arxiv.org/abs/2611.07477)
*Alexander Magro,Aristotle Martin,Ye Wang,Wen Chen*

Main category: cs.DC

TL;DR: KOSMOS 是一个"自调度持久化内核"(self-scheduling persistent kernel)库：把所有 workgroup 放在一个持久化 launch 里，不再区分通信/计算角色，而是通过按消费者需求排序的队列，让各 workgroup 随数据就绪情况在 NCCL/集合通信角色与 GEMM 角色之间动态切换，从而消除 TP+SP、EP 中固定分工/固定切分导致的空闲窗口。它把 transformer 层的每个 TP+SP 集合通信与其 GEMM 融合，并把整层 expert 层(router→fold)压成每方向一次 launch。在 AMD MI350X / MI355X 上，Megatron-LM 端到端训练 TP+SP 加速 1.10–1.28x (BF16)、1.10–1.25x (MXFP8)；DeepSeek-V3 与 Qwen3-235B proxy 端到端训练相对 DeepEP 加速 1.29–1.83x。


<details>
  <summary>Details</summary>
Motivation: TP+SP 与 EP 把集合通信放在 transformer 层的关键路径上，通信与计算在时间上串行或被固定比例切分。现有 fused kernel 用固定的角色分配(哪些 SM 做通信、哪些做计算)或固定调度/固定通信-计算切分，无法跟随实际数据到达时间，留下大块 idle window；而静态预测的 split 也无法自适应数据就绪度，且在异构/可变负载下失准。动机是把调度权从"编译期/启动期决定"下移到"运行时由数据就绪驱动"，即用去中心化的队列机制替代集中式 scheduler 与 per-call 代价模型。

Method: 1) 持久化内核(self-scheduling persistent kernel)：一次 launch 内驻留全部 workgroup，无 grid 级 scheduler，无 per-call cost model，无手调 split。2) Workgroup 角色可变：每个 workgroup 可在通信(集合通信 producer/consumer)与 GEMM 计算之间切换，角色由"按消费者需求排序的队列"(consumer-demand-ordered queues)决定优先级，本质是一个硬件友好的分布式工作窃取/需求驱动调度器，用队列顺序近似优先级而非全局调度。3) 融合粒度：把 transformer 层所有 TP+SP collective 与其相邻 GEMM 融合到同一 launch，通信 tile 就绪即被计算 workgroup 消费，反之计算产出即被推入通信队列。4) EP 路径：整个 expert 层从 router(含 dispatch/all-to-all)到 fold(combine + 加权求和)在每方向一次 launch 内完成，避免多次 kernel launch 与中间 host 同步。5) 平台面向 AMD CDNA(MI350X/MI355X)，即依赖高带宽跨 workgroup 通信(如 LDS/共享内存队列、全局内存原子/flags)与可编程的 workgroup 级同步。

Result: 在 AMD Instinct MI350X 与 MI355X 上：Megatron-LM 中 TP+SP 端到端训练加速 1.10–1.28x(BF16)、1.10–1.25x(MXFP8)；DeepSeek-V3 与 Qwen3-235B 规模 proxy 的端到端训练相对 DeepEP 加速 1.29–1.83x。加速来自消除 idle window 与 launch/同步开销，而非提高单 kernel 峰值效率；收益在通信-计算比高(EP、大 TP)与低精度(MXFP8)下更明显。

Conclusion: KOSMOS 表明：通信-计算重叠的瓶颈不在静态切分精度，而在调度权的归属——把角色决策下放到 workgroup 级、由数据就绪与消费者需求驱动，可在不引入全局 scheduler 和代价模型的前提下显著压缩关键路径空闲。系统贡献是把"persistent kernel + 需求排序队列"做成可复用的通信原语融合库(TP+SP 融合 GEMM、整层 EP 单 launch)，在 AMD 平台上给出了端到端训练加速实证。工程影响：对框架侧意味着 collective 与 GEMM 的融合点从库层(NCCL/RCCL + cuBLAS/Tensile)上移到 kernel 内，调度从 host/编译器静态决定转为运行时数据驱动；对可移植性提出新问题(强依赖 AMD workgroup 编程模型与设备内细粒度同步，迁移到 NVIDIA 需重新设计 DSMEM/cluster 与 cooperative launch)；对可观测性提出要求(队列深度、角色切换率、idle 归因成为新指标)；也暗示未来通信库需暴露更细粒度的 tile 级接口而非整 tensor collective API。

Abstract: Tensor and sequence parallelism (TP+SP) and expert parallelism (EP) put collectives on the critical path of transformer layers. State-of-the-art fused kernels mitigate this with fixed roles or schedules, but this rigidity leaves large idle windows. Predicting a communication-computation split does not remove them either; a predetermined split cannot follow data readiness. We present KOSMOS, a library for self-scheduling persistent kernels whose workgroups use queues ordered by consumer demand to switch between communication and computation roles as data become ready, with no scheduler, per-call cost model, or tuned split. KOSMOS fuses every TP+SP collective of a transformer layer with its GEMM, and runs an entire expert layer, from router to fold, in one launch per direction. Evaluated on AMD Instinct MI350X and AMD Instinct MI355X GPUs, KOSMOS speeds up TP+SP end-to-end training in Megatron-LM by 1.10-1.28x in BF16 and 1.10-1.25x in MXFP8. KOSMOS accelerates end-to-end training of DeepSeek-V3 and Qwen3-235B proxies by 1.29-1.83x over DeepEP.

### [3] [DMuon: Scaling Matrix Optimizers in Data Parallelism with Topology-Aware Matrix Ownership and Communication](https://arxiv.org/abs/2611.07084)
*Starrick Liu,Ruizhi Chengze,Lufang Chen,Michael Zhao,Ran Yu,Xiaofan Li,dance kuzi,Yue Zhang,Zijuan Lin,SongAo Han,YongHua Chen,Ruyi Gan,Hao Wang*

Main category: cs.DC

TL;DR: DMuon 是一个面向 PyTorch FSDP（ZeRO-2/3）与 HSDP 的矩阵粒度优化器运行时：为每个权重矩阵分配唯一 owner，由 owner 在完整矩阵上执行 Newton–Schulz 迭代与优化器更新，并按计算代价做负载均衡；在 HSDP 上 ownership 全局唯一，使梯度与优化器状态只保留一份，并把就绪参数跨节点发布与后续计算重叠；同时把变长稀疏 collective 按数据就绪调度并沿两级网络拓扑路由。256 张 H100 上吞吐中位数达 FSDP2+AdamW 的 1.05×，为 gather-then-replicate Muon 基线的 2.1×。


<details>
  <summary>Details</summary>
Motivation: 矩阵级优化器（Muon 等）需要对整个权重矩阵做正交化/NS 迭代，这与数据并行运行时按元素/行分片参数的假设冲突。一旦参数也被分片（ZeRO-3/FSDP），矩阵优化器就必须额外通信（all-gather 完整矩阵）或重复计算（各 rank 各自重算），在 Muon 上形成明显的通信与计算开销，使其难以与生产级 FSDP 栈结合。

Method: 1) Matrix ownership：每个矩阵由唯一 owner 负责完整 NS 迭代与更新，参数仍可分片存储但计算不切分；2) 代价感知的分区算法把矩阵分配到各 owner，使各 rank 的 NS FLOPs 与更新工作负载均衡；3) HSDP 下 ownership 在 replica 间全局唯一，集群只保留单份梯度/优化器状态，并在参数更新完成后立即跨节点发布，与后续计算重叠（不等待全局屏障）；4) 通信量呈变长、稀疏特征，运行时改为按数据就绪触发变长 all-gather（参数发布）与稀疏/分段 reduce-scatter（梯度归约），并按集群两级网络（节点内 NVLink / 节点间 IB）分层路由；5) 与 FSDP2 的 sharding/DTensor 栈集成，ZeRO-2/3 与 HSDP 均可插拔。

Result: 在最多 256 张 H100 上，3 个 dense LLM 与 2 个 VLA 模型评测：256 GPU 时吞吐中位数为 FSDP2+AdamW 的 1.05×（即与 AdamW 训练持平或更优），说明参数 gather 与梯度归约的优化吸收掉了矩阵优化器的额外通信与计算；相对 gather-then-replicate Muon 基线，吞吐中位数为 2.1×。

Conclusion: 矩阵级优化器不必以吞吐为代价嵌入分片数据并行栈；把“优化单元”与“存储分片单元”解耦，用全局唯一 owner 表示 + 就绪即发布 + 拓扑感知的变长 collective 调度，可在 HSDP 大规模集群上实现与 AdamW 相当的训练效率，并显著优于朴素 gather-then-replicate 实现。对工程而言，这是给 Muon 类优化器提供了一条可直接接入 PyTorch FSDP2 生态的低开销落地路径，也提示 ZeRO-3 下的优化器状态/梯度通信模式可围绕“单位置计算 + 异步发布”重构。

Abstract: Matrix optimizers such as Muon update whole weight matrices, which conflicts with the element- or row-wise sharding of data-parallel runtimes. Once parameters are sharded as well, matrix optimizers incur extra communication or repeated computation. We present DMuon, a matrix-granular optimizer runtime for PyTorch FSDP (ZeRO-2/3) and HSDP. DMuon assigns each matrix a unique owner, which performs the Newton--Schulz (NS) iteration and optimizer update on the full matrix, and balances the load across owners by computational cost. On HSDP, ownership is global across replicas, so the cluster keeps a single copy of gradients and optimizer state, and updated parameters are published across nodes as soon as they are ready, overlapping subsequent computation. This layout makes every collective sparse and variable in length, so DMuon schedules these collectives as their data becomes ready and routes them along the cluster's two-level network. On up to 256 H100 GPUs, across three dense LLMs and two VLA models, DMuon matches or exceeds the training throughput of PyTorch FSDP2 with AdamW, reaching 1.05$\times$ that of FSDP2 with AdamW at the median on 256 GPUs. The optimized parameter gathering and gradient reduction absorb the extra communication and computation a matrix optimizer requires. Against a gather-then-replicate Muon baseline, DMuon's throughput is 2.1 times as high at the median.

  <summary>Details</summary>

This view explains which models benefit from AFD, and shows that speculative decoding helps light-expert models most, where the enlarged overlap gain outweighs the larger disaggregation cost and adds a further 8% to AFD's advantage over wide EP. FastAFD is open source at https://github.com/hao-ai-lab/FastAFD.
