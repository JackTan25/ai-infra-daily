### [1] [One-Sided Expert-Parallel All-to-All for Mixture-of-Experts Inference over NVLink](https://arxiv.org/abs/2611.13188)
*Bo Li,Chulian Zhang,Or Biri,Anthony Chang,Anton Korzh,Noam Duvdevani,XingFei Xi,Daniel Stokes,Zhenhuan Chen,Ludwig Schneider,Artem Y. Polyakov,Julien Demouth,Chandler Zhou*

Main category: cs.DC

TL;DR: NVLinkOneSided 是一种面向单 NVLink 域内 GPU 的单边（one-sided）专家并行 all-to-all 通信方案。它免去元数据交换，把源 rank 的 token 直接 push 到目标 GPU 上按 rank-major 布局的缓冲区，并让 grouped GEMM 原地读取，从而消除 per-expert 拷贝。提供 Fence 与 Sentinel 两种同步协议分别面向高吞吐与低延迟场景。在 Blackwell 上，dispatch/combine 比 DeepEP 快 1.2–3.0×（小 batch 最显著），MoE 层端到端比 DeepEP+DeepGEMM 快至多 2.4×，在 ≤128 tokens/GPU 时甚至优于融合的 DeepGEMM MegaMoE，因此对 decoding 场景仍具竞争力。


<details>
  <summary>Details</summary>
Motivation: MoE 的 EP 每层需要 dispatch 与 combine 两次 all-to-all。推理阶段每 GPU 每次处理的 token 数远少于训练，此时延迟由不随 token 数增长的固定开销（元数据交换、同步、建链、拷贝/重排等）主导，而非数据搬运量。现有实现（DeepEP 等）在这一 regime 下固定成本占比过高，且与计算后端耦合、需按 expert 重新布局数据，造成额外拷贝。

Method: 1) 单边 push：源 rank 无需先交换元数据（免握手/免计数协商），直接将 token 写入目标 GPU 的 rank-major 缓冲区，把通信与元数据传播合并为一次写。2) 布局与计算融合：grouped GEMM 直接在 rank-major 缓冲区原地读取 token，避免生成 per-expert 副本，省去一次 HBM 级别的数据重排。3) 两套同步协议：Fence 协议（基于 fence/可见性语义的批量同步，面向高吞吐、大 batch）与 Sentinel 协议（标记位轮询式细粒度同步，面向低延迟、小 batch）。4) 模块化接口：与激活量化格式无关（quantization-agnostic），与 MoE 计算后端解耦，便于接入推理框架。

Result: Blackwell GPU 上：dispatch+combine 比 DeepEP 快 1.2–3.0×，加速比在小 batch 时最大；配合 DeepGEMM 的 MoE 层端到端加速至多 2.4×；在 ≤128 tokens/GPU 时性能超过融合式 DeepGEMM MegaMoE，表明在 decoding 阶段仍具竞争力。接口为模块化设计，支持不同量化格式并可与不同 compute backend 组合。

Conclusion: 该工作表明推理期 EP 的瓶颈是固定开销而非带宽，因此“消除元数据交换 + 原地消费 + 按场景选择同步协议”的单边通信设计能在小 batch 下取得显著收益。工程上，它降低了 MoE 推理的延迟下限，使 EP 在小 batch/decoding 场景下可与张量并行及融合 kernel 竞争；模块化接口有利于在推理框架中替换与增量部署。适用范围限于单个 NVLink 域（节点内/超节点），跨域仍需回到基于 RDMA/NVLink 分层的方案；同步协议的正确性与可见性语义在长尾负载与负载不均衡 expert 分布下的鲁棒性需进一步验证。

Abstract: Expert parallelism (EP) shards the experts of a Mixture-of-Experts (MoE) layer across GPUs, so every MoE layer requires two all-to-all communications, namely dispatch and combine. Compared with training, inference processes relatively few tokens per GPU at a time, and at small batch sizes fixed costs that do not grow with the number of tokens, rather than data movement, dominate the latency. We present NVLinkOneSided, a one-sided EP all-to-all for GPUs within a single NVLink domain. Each source rank pushes its tokens, without first exchanging metadata, into rank-major buffers on the target GPUs, and the grouped GEMMs read them in place instead of from a per-expert copy. We provide two protocols for the synchronization that the communication requires, namely Fence and Sentinel, for high-throughput and low-latency scenarios respectively. On Blackwell GPUs, NVLinkOneSided completes dispatch and combine 1.2-3.0$\times$ faster than DeepEP, with the largest speedups at small batch sizes. The resulting MoE layer is up to 2.4$\times$ faster than DeepEP with DeepGEMM. It even outperforms the fused DeepGEMM MegaMoE at up to 128 tokens per GPU, making it still competitive for decoding. We expose NVLinkOneSided through a modular interface, so that it is agnostic to the activation quantization format, decoupled from the MoE compute backend and easy to integrate into inference frameworks.

### [2] [Scaling Shapley Energy Attribution to Large LLM Batches](https://arxiv.org/abs/2611.13802)
*Qi Luo,Ziwen Wang,Kunlin Li,Changxi Liu,Yun Chen*

Main category: cs.DC

TL;DR: StepSplit 通过将每个推理 step 的能耗分解为"共享能耗（主要来自读取模型权重）+请求专属能耗"，推导出 Shapley 值的闭式解：每个请求只承担自身能耗加其在每个参与 step 中均摊的共享能耗。仅需一次 2.5–17.8 分钟的微基准即可按模型/GPU 组合完成标定；静态 batching 下扫描一遍调度日志即可，连续 batching 下再用 CPU 重放调度器做修正。以 529,513 次 GPU 实测 Shapley 值为基准，L1 误差仅 0.4–6.4%，而按 token 比例分摊为 13.4–71.7%。


<details>
  <summary>Details</summary>
Motivation: LLM 服务需要按请求做资源计量（计费）归因，能耗是关键成本指标；但 serving engine 采用 batching，GPU 只上报聚合能耗，缺乏请求级能耗数据。工业界常用的 token 比例分摊在 batching 下明显不公（因为 step 能耗中相当大比例是与请求无关的固定开销，如权重读取）。理论上 Shapley 值能给出公平分摊，但精确计算对 N 个请求需 2^N−1 次 GPU 运行，大 batch 下不可行。论文要在"公平性"与"可计算/低成本"之间搭桥。

Method: 1) 关键观察：单 step（一次 batch 前向）能耗可近似为 E_step = E_shared + Σ_i E_i，E_shared 主要由权重读取构成、与 batch 组成基本无关，E_i 为请求相关项。2) 在该可加结构下推导 Shapley 值闭式解：请求 i 的份额 = E_i + Σ_{step∈S_i} E_shared/|step|，即自身能耗 + 各参与 step 共享能耗的等分。3) 标定：每个 (模型, GPU) 组合跑一次 2.5–17.8 分钟 microbenchmark，拟合 E_shared 与 E_i（按序列长度/形状的模型）。4) 静态 batching：单次遍历 scheduler log 直接套闭式解，O(1) 分摊开销。5) 连续 batching：移除某请求会改变后续 batch 组合，故闭式解加上一个修正项，修正通过在 CPU 上重放调度器（无需额外 GPU 运行）计算。6) 评测：用 529,513 次实测 GPU run 得到参考 Shapley 值做对照。

Result: 静态 batching（batch size 8–256）：StepSplit L1 误差 0.4–4.3%，token 比例分摊 13.4–61.3%。连续 batching（8–128 请求）：StepSplit 0.5–6.4%，token 比例分摊 20.6–71.7%。误差随 batch 增大而略有上升（共享/专属分离假设与修正近似带来的残差），但整体较基线降低约一个数量级以上，且额外 GPU 开销仅为每配置一次亚 20 分钟标定。

Conclusion: 论文的系统贡献在于：把"公平的请求级能耗归因"从不可行的指数级 Shapley 计算，转化为基于 step 能耗可加结构的闭式分摊 + 一次性离线标定 + 调度器 CPU 重放修正，使能耗计量可在线/离线低成本地接入 LLM serving 的计费链路。工程意义：为多租户 serving 提供可解释、可审计的能耗账单与调度/定价信号（如对长上下文、长解码请求的能耗感知路由与批处理策略），并可扩展到能耗以外的其他"固定+可变"成本归因（权重读取、KV cache 占用）。

Abstract: LLM services have become essential infrastructure for applications such as chat assistants and coding agents. Service providers need to attribute resource consumption to individual requests for purposes such as billing. Among these resources, energy is a key metric for assessing the cost of serving each request. However, serving engines batch requests together, and GPUs report only aggregate energy consumption. Providers typically estimate each request's share in proportion to its token consumption, but this approach can produce substantially unfair estimates. The Shapley value provides a principled solution to fair energy allocation, but computing it directly requires $2^N-1$ GPU runs for $N$ requests, which is infeasible for large batches.
  To address this problem, we propose StepSplit. Across GPU generations, we observe that the energy consumed by each inference step, a forward pass over a batch, consists of a shared energy, largely due to reading model weights, and a request-specific energy. We derive a closed-form Shapley value: each request is charged its own energy plus an equal part of the shared energy of every step in which it participates. A microbenchmark of 2.5-17.8 minutes calibrates both parts of the step energy once per model and GPU configuration. Under static batching, StepSplit uses this closed form in a single pass over the scheduler log. Under continuous batching, removing a request can change how the remaining requests are batched, so StepSplit adds a correction to the closed form, computed by replaying the scheduler on a CPU. We evaluate StepSplit against Shapley values measured using 529,513 GPU runs. Under static batching with batch sizes of 8-256, StepSplit achieves an $L_1$ error of 0.4-4.3%, compared with 13.4-61.3% for token-proportional allocation. Under continuous batching with 8-128 requests, the corresponding errors are 0.5-6.4% and 20.6-71.7%.
