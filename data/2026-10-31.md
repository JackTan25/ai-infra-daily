### [1] [A Comparative Study of Parallel Implementations of Short-Time Fourier Transform](https://arxiv.org/abs/2610.38069)
*Minh Chau Nguyen,Marcelo Ponce*

Main category: cs.DC

TL;DR: 该文对两类并行短时傅里叶变换（STFT）算法——基于FFT的实现与准并行前馈（quasi-parallel feedforward）实现——在共享内存、分布式内存、以及分布式-共享混合三种并行模式下进行了实现、对比与性能刻画，揭示了二者在运行时、可扩展性、内存占用、通信开销与串行比例上的权衡。


<details>
  <summary>Details</summary>
Motivation: FFT 本身已有成熟的并行化与调优研究，但 STFT 作为"滑动窗 + 多次 FFT"的时频分析核心算子，其并行实现与性能特征缺乏系统性认识：现有工作少有对多种并行 STFT 算法在不同并行编程模型下的横向对比，也缺乏对瓶颈（计算/通信/内存）的定量归因，导致工程上难以选型与调优。

Method: 实现并对比两种 STFT 并行算法：（1）FFT-based 方法，即按窗分帧后对每帧调用并行 FFT；（2）quasi-parallel feedforward 方法，采用类前馈/递归结构的准并行公式。两种算法各实现三种并行版本：共享内存（多线程）、分布式内存（消息传递，如 MPI）、以及分布式-共享混合（MPI+X 线程）。通过改变并发度进行强/弱扩展性测试，测量运行时与内存占用，并用 profiler 分析计算时间、通信开销占比，识别瓶颈类型（compute-bound vs. 通信/内存受限），并估计串行分数以解释扩展性差异。

Result: （1）低并发度下 quasi-parallel feedforward 算法运行时更优；（2）随并发度提高，FFT-based 算法扩展性更好且内存占用更低；（3）除 hybrid feedforward 变体外，所有实现均为 compute-bound；（4）分布式内存变体的通信开销显著更高；（5）feedforward 类算法串行比例较高，限制了其可扩展性。总体上，FFT-based 以内存效率取胜，feedforward 以低并发下的低延迟取胜。

Conclusion: 该研究给出了并行 STFT 不同算法族的"定义性特征"画像：FFT-based 内存占用低、可扩展性好，适合高并发、内存敏感的规模化时频分析；准并行前馈算法低并发延迟低但串行分数高、通信/扩展性受限，适合小规模或低延迟场景。结论为并行 STFT 的算法选型与并行模型（共享/分布式/混合）选择提供了实证依据。局限在于：未涉及 GPU/加速器与异构实现，也未讨论异步、流水线/重叠通信、批处理与向量化等现代优化手段，且评测集中于单一硬件与问题规模。对训练/推理系统而言，该工作的方法论（多算法×多并行模型的瓶颈归因与串行分数分析）可直接迁移到数据预处理与信号特征提取流水线的性能工程。

Abstract: The short-time Fourier transform (STFT) computes the Fourier transform of a short-duration window of a longer signal, which characterizes how a frequency changes over time. While the Fourier transform algorithms, particularly the Fast Fourier Transform (FFT) algorithm, has been well developed to take advantage of parallel computing, there is limited work on understanding the performance of parallel short-time Fourier transform algorithms. In this study, two parallel short-time Fourier transform algorithms, one is FFT-based and the other a quasi-parallel feedforward algorithm, are implemented and analyzed in comparison with each other. It is found that while the quasi-parallel algorithm outperforms in runtime under low concurrency settings, the FFT-based algorithm scales better and has lower memory usage. For each algorithm, three parallel approaches, shared-memory, distributed-memory and hybrid distributed-shared-memory, are tested. Profiling results show that all implementations are compute bound except for the hybrid feedforward algorithm, and that the distributed-memory variants incur significantly higher communication cost. Overall, this study presents a deeper and more comprehensive analysis and demonstrates the defining characteristics of different families of parallel short-time Fourier transform algorithms, in which the FFT-based approach uses less memory while the quasi-parallel feedforward algorithm has lower runtime but higher serial fraction.

### [3] [Only Accepted Tokens Count: An Energy Accounting of Speculative Decoding Under Latency Targets](https://arxiv.org/abs/2610.40287)

Main category: cs.DC

<details>
  <summary>Details</summary>

Energy per token determines how many tokens a datacenter can serve, while a latency target bounds how quickly each user receives them. During decode, every weight is read from memory for every generated token. Batching amortizes this read across users but makes no individual user faster. Speculative decoding does: a drafter proposes several future tokens, and the target model verifies them in a single forward pass that reuses the same weight read. Because every drafted token must be verified whether or not it is accepted, the energy speculation saves depends on how many drafted tokens are accepted. This saving is hard to pin down. It varies across target models from different attention families and across drafting schemes, and it depends on the text being served. Meeting a tighter latency target with speculation then costs additional energy. Larger batches lower energy per token without speculation. Speculation adds to that saving only when acceptance is high, and on the model we tested it leaves little headroom for latency-preserving DVFS.
