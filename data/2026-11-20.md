### [1] [Twindex: Index Cache Offloading with Coarse-to-Fine Selection for Long-Context Sparse-Attention Serving](https://arxiv.org/abs/2611.25078)
*Yuxuan Xia,Jiakun Fan,Han Meng,Hao Mark Chen,Shenji Wan,Dongsheng Yang*

Main category: cs.DC

TL;DR: Twindex 指出现有 sparse-attention 服务系统中，indexer cache 已成为 HBM 瓶颈（1M token 时占单请求 HBM 的 63%–75%），因此将 indexer cache 的紧凑压缩副本常驻 HBM、完整 cache 放在 host memory，两步检索（HBM 副本选候选 → host 原始行精排 top-k），且不改权重、可嵌入 CUDA graph。


<details>
  <summary>Details</summary>
Motivation: 长上下文 decode 的并发度受 HBM 容量约束。Sparse-attention 模型（Qwen3.8-Flash-Next、DeepSeek V4.1-Flash、GLM-5.2）引入 indexer：每步需用 indexer cache 对所有历史 index 条目打分，再据 top-k 读取主 KV。当服务系统把主 KV offload 到 host memory 后，主 KV 不再占 HBM，indexer cache 反而成为新的 HBM 瓶颈（Qwen 63%、V4.1 75% @1M），直接限制 batch size 与吞吐。

Method: 1) 双副本分层放置：HBM 只放 indexer cache 的紧凑副本，完整 indexer cache 留在 host memory；2) 两级检索：紧凑副本先产出超集候选集（大于 k），再在 host memory 中取这些候选对应原始行，由模型原生 indexer 完成精确 top-k，保证选出的 row 与原始 indexer 语义一致；3) 紧凑副本 = 可学习共享分量 + 压缩残差，离线训练一次（不改模型权重）；4) 全流程在 CUDA graph 内执行，候选检索—host 行读取—精排均为静态图可捕获操作；5) 请求级私有 index（不共享 indexer state），仅 Qwen/GLM 的 prefix 主 KV 在 host memory 中共享。

Result: 1M token、现代 GPU 下：可容纳请求数为仅 KV offload 方案的 1.78×（Qwen）、1.62×（V4.1）、3.03×（GLM-5.2）；在 host memory 不成为 batch 上限时，decode 吞吐为 1.44×/1.25×/2.54×。精度上 benchmark 平均分最多比 baseline 低 3.1%。

Conclusion: 该工作把长上下文服务的容量瓶颈从"主 KV"转移到"indexer cache"，并给出可落地的分层索引压缩方案：在几乎无损（≤3.1%）的前提下显著提升并发与 decode 吞吐。工程上意味着 sparse-attention serving 的系统设计需要把 indexer 与 main KV 视作两级独立可 offload 的对象，索引侧的近似检索（先粗筛后精排）+ CUDA graph 友好的数据流是提升长上下文性价比的关键杠杆。

Abstract: In long-context decoding, GPU memory (HBM) caps how many requests a GPU decodes at once. Sparse-attention models such as Qwen3.8-Flash-Next, DeepSeek V4.1-Flash and GLM-5.2 add an indexer: at every step it scores all past index entries with its own indexer cache, and attention reads the main KV of only the top-k entries. We find that once serving systems move the main KV to host memory, the indexer cache becomes the HBM bottleneck, at 63% of per-request HBM on Qwen and 75% on V4.1 at 1M tokens. Therefore, we introduce Twindex, which keeps only a compact copy of the indexer cache in HBM and the full indexer cache in host memory. At each step, the copy selects a larger candidate set, and the model's own indexer picks the top-k from the original rows of the candidates in host memory. The copy combines the shared component with the compressed residuals, both learned once offline. Twindex changes no model weights and runs inside CUDA graphs. At 1M tokens on modern GPUs, Twindex fits $1.78\times$, $1.62\times$ and $3.03\times$ as many requests as KV offloading alone on Qwen, V4.1 and GLM-5.2, and reaches $1.44\times$, $1.25\times$ and $2.54\times$ decode throughput when host memory does not limit the batch. Every request keeps its own index, and Qwen and GLM requests share prefix main KV in host memory. In our evaluations, mean benchmark scores are at most 3.1% below the baseline's.

### [2] [Berth: SLO-Preserving GPU Sharing Without New Preemption](https://arxiv.org/abs/2611.25091)

Abstract: Inference services keep GPUs reserved for their worst-case load, and most of that capacity sits idle. Filling it with best-effort work such as training is the obvious remedy, and latency is why it rarely happens: on a shared GPU, a request that must finish within milliseconds finds the best-effort job's kernels running or queued ahead of it. Spatial sharing cannot evict them, temporal sharing gives the request only its turn, and hardware partitioning protects it by idling what it does not use. Systems that keep both the SLO and the utilization have reached inside the stack (rewriting kernels, patching the driver, instrumenting the framework), which the operator of a closed GPU stack cannot do. This paper argues that reaching inside is unnecessary. The time-slicer built into commodity GPUs already preempts a running kernel within a fraction of a millisecond and switches the moment a context runs out of work; what it lacks is priority, and priority can be created from outside by controlling what the best-effort context has to run. ### [3] [TripleKV: Predict, Prefetch, Protect -- KV Cache Management for AI Agents](https://arxiv.org/abs/2611.25112)
*Shashwat Jaiswal,Chloe Alverti,Mengmei Ye,Chen Wang,Hubertus Franke,Fan Lai,Tianyin Xu,Josep Torrellas*

<details>
  <summary>Details</summary>
Motivation: Agent 工作负载在推理与工具执行之间交替，反复复用不断增长的上下文。高并发下 KV cache 工作集可达数百 GiB，远超 GPU 显存；空闲 KV block 被逐出到更慢的存储层后，返回的 agent 需要昂贵的数据回取，导致推理被阻塞（抬高了 TTFT 与关键路径 SSD 读取比例）。

Method: 三点设计：(1) 工具感知延迟预测器估计每个工具调用的完成时间，在预测的重用时刻之前把所需 KV block 从 SSD 预取进 host DRAM（而非 GPU HBM），避免占用稀缺显存、避免干扰并发推理请求；(2) 消除 GPU 常驻 block 在 DRAM 中的副本重复，提高 DRAM 有效容量；(3) victim-cache 机制，当 block 从 GPU 显存被逐出时从 SSD 回填，提升多级缓存的命中连续性。

Conclusion: Agent 负载中 KV 复用的"确定性内容 + 不确定时刻"特性使预测式预取可行；把预取目标层选在 DRAM 而非 GPU，是兼顾显存紧张与并发干扰的关键权衡，TripleKV 由此把多级 KV 存储的延迟开销基本转出关键路径。

TripleKV uses a tool-aware latency predictor to estimate when each tool call will complete and prefetches the required KV blocks from SSD into host DRAM ahead of time. Unlike GPU prefetching, this avoids reserving scarce GPU memory and interfering with concurrent inference requests. To further improve DRAM utilization, TripleKV eliminates duplication of GPU-resident blocks in DRAM, and introduces a victim-cache mechanism that refills blocks from SSD upon their eviction from GPU memory.
