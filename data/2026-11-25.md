### [1] [MemVanta: Memory-Efficient CPU Inference for Quantized GGUF Language Models](https://arxiv.org/abs/2611.27997)
*Saurav Singla,Aarav Singla,Advik Gupta,Parnika Gupta*

Main category: cs.DC

TL;DR: MemVanta 是一个以“内存驻留”为首要系统目标的实验性 C++20 CPU 推理运行时，面向量化 GGUF 模型，集成 mmap 访问、有界张量缓存、量化执行路径、分页 KV 状态与显式内存压力校验。在 OpenLLaMA 7B v2 Q4_0、纯 CPU 场景下，其峰值 RSS 为 3.98 GiB，比 llama.cpp 的 7.59 GiB 降低 47.50%，但吞吐大幅下降（prefill 3.15 vs 45.82 tok/s，decode 1.52 vs 7.76 tok/s）；在 cgroup-v2 无 swap 环境下可在 3584 MiB 上限内完成执行，而 llama.cpp 在该上限被 OOM-kill、需 3840 MiB 才成功。


<details>
  <summary>Details</summary>
Motivation: 商品 CPU 上部署量化 LLM 时，瓶颈往往不只是算力，而是固定内存预算下的常驻内存占用；现有主流运行时（llama.cpp）以吞吐优先，缺少把内存驻留作为一等系统目标的设计与可复现评测，边缘/容器化场景缺少在硬内存上限内可预测运行的方案。

Method: 系统机制上以内存驻留为设计中心：(1) 内存映射（mmap）方式访问 GGUF，避免权重整体加载到匿名页；(2) 有界张量缓存，限制同时常驻的解量化/中间张量规模；(3) 量化执行路径，直接在 Q4_0 上计算；(4) 分页 KV 状态（paged KV）按需分配/回收；(5) 显式内存压力校验。实验采用同一 OpenLLaMA 7B v2 Q4_0 GGUF、纯 CPU，对照固定版本的 llama.cpp 基线；预热后测 5 次取均值与方差，统计峰值 RSS 与 prefill/decode 吞吐；另做 Linux cgroup-v2 且关闭 swap 的内存上限测试，逐级下探可完成执行的最小上限。

Result: 峰值 RSS 3,983,412 KiB 对 7,586,960 KiB，降低 47.50%。吞吐：prompt processing 3.15±0.04 tok/s 对 45.82±0.96 tok/s；token generation 1.52±0.02 tok/s 对 7.76±0.09 tok/s（分别约 14.5× 和 5.1× 的差距）。cgroup-v2 无 swap：MemVanta 在 3584 MiB 上限下完成执行；llama.cpp 在该上限被 OOM-killed，首次成功于 3840 MiB。

Conclusion: MemVanta 的定位是内存效率研究原型而非吞吐竞争者：它证明在 CPU 推理栈中把常驻内存作为显式调度目标，可以换来约一半的峰值 RSS 下降与更低的可运行内存下限，代价是显著的性能退化。工程价值在于给出了“内存上限优先”的可复现实验范式（固定 GGUF、固定基线、cgroup 硬限下探），并在容器/边缘部署中把 OOM 风险转化为可预测的降速运行；后续需通过机制级消融与页错误/带宽剖析把吞吐损失归因到具体设计，并探索自适应缓存容量与分层驻留（热权重常驻、冷权重按需映射）以收窄性能差距。

Abstract: Deploying large language models on commodity CPUs is often constrained not only by computational throughput but also by the resident memory required to execute quantized models within fixed system budgets. We present MemVanta, an experimental C++20 inference runtime for quantized GGUF language models that treats memory residency as a first-class systems objective. MemVanta combines memory-mapped model access, bounded tensor caching, quantized execution paths, paged key-value state, and explicit memory-pressure validation. These results position MemVanta as a memory-efficiency research prototype rather than a throughput competitor. We analyze the architectural mechanisms underlying this trade-off and discuss reproducibility, correctness, limitations, and opportunities for memory-constrained CPU and edge inference.

*Xuan Zhang,Haisheng Tan,Han Tian,Jialiang Huang,Yuteng Wang*

Main category: cs.DC

TL;DR: CCAMoE is a unified MoE inference runtime that couples cache-only speculative drafting with draft-guided, overlapped expert-cache prefetching and a cost-aware draft-length controller, achieving up to 2.33x decoding speedup over SOTA expert-offloading baselines.


<details>
  <summary>Details</summary>
Motivation: Memory-constrained GPUs must offload MoE experts to CPU, so decoding is bottlenecked by expert transfers over PCIe/NVLink and slow CPU-side expert execution. Speculative decoding can amortize these costs by accepting multiple tokens per expensive step, but existing approaches fail: separate draft weights compete for the already scarce GPU memory, and simply lengthening drafts increases verification cost (more experts touched, more transfers), eroding the benefit. The paper argues these two concerns—drafting and expert-cache management—are currently solved in isolation and must be co-designed.

Method: Three coordinated mechanisms sharing one evolving expert cache: (1) Cache-only drafting—reuses already-resident target experts (no auxiliary draft model) to produce proposal tokens and routing hints; the proposal itself implicitly predicts the next layer's routing. Co-designing them converts an extra memory cost into a prefetch signal and a latency win. Practically, this suggests MoE serving stacks on memory-constrained GPUs (single-node multi-GPU or consumer/prosumer hardware) should expose routing predictions and cache residency to the speculative scheduler. Open questions left implicit by the abstract: robustness of routing hints across layers/models, sensitivity to HBM capacity and CPU expert throughput, and interaction with batching and inter-token parallelism.

Together, these mechanisms coordinate proposal generation and cache preparation through a shared evolving cache, improving proposal quality while reducing verification cost. Across various MoE models, GPU platforms, and workloads, CCAMoE consistently achieves the lowest decoding latency, with up to 2.33$\times$ speedup over state-of-the-art baselines.
