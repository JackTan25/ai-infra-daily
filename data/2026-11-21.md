### [1] [Twindex: Index Cache Offloading with Coarse-to-Fine Selection for Long-Context Sparse-Attention Serving](https://arxiv.org/abs/2611.25078)
*Yuxuan Xia,Jiakun Fan,Han Meng,Hao Mark Chen,Shenji Wan,Dongsheng Yang*

Main category: cs.DC

TL;DR: Twindex 指出：在长上下文解码、主 KV 已卸载到主机内存的场景下，稀疏注意力模型的 indexer cache 取代主 KV 成为 HBM 瓶颈（Qwen 上占单请求 HBM 63%，V4.1 上 75%）。Twindex 在 HBM 只保留 indexer cache 的紧凑副本（共享分量 + 离线学习的压缩残差），完整 indexer cache 留在主机内存；每步先用副本选出更大的候选集，再由模型原 indexer 在主机端候选原始行中选出 top-k，不改权重、可在 CUDA graph 内运行。1M token 下可并发请求数为纯 KV 卸载的 1.78×/1.62×/3.03×，吞吐为 1.44×/1.25×/2.54×，精度平均最多下降 3.1%。


<details>
  <summary>Details</summary>
Motivation: 长上下文解码的并发上限由 HBM 决定。稀疏注意力（DeepSeek Sparse Attention 类）虽只读取 top-k 主 KV，但每步仍需用 indexer cache 对所有历史 index 条目打分，因此 indexer cache 随序列线性增长。当服务系统把主 KV 卸载到主机内存后，indexer cache 反而成为剩余 HBM 占用的大头（1M token 时 Qwen 占 63%、V4.1 占 75%），限制了 batch size 与吞吐。论文的动机就是把这块"元数据"级缓存的 HBM 占用压下来，同时不改变 top-k 选择质量。

Method: 核心思想是"两层索引 + 候选放大"：HBM 中只放 indexer cache 的紧凑副本，完整的 indexer cache 保存在主机内存（NUMA 友好的 pinned 内存、每请求私有）。紧凑副本由两部分构成——一个是离线学习一次的共享分量（跨请求/层共享的低秩基），另一个是压缩残差，两者合起来近似原 indexer 向量。每步解码时：① 用 HBM 副本对全部历史 entry 做低成本打分，选出比 k 更大的候选集（k' > k，留出召回余量）；② 按候选索引在主机内存取回原始 indexer 行，用模型自身的 indexer 打分逻辑精确选出 top-k；③ 再用 top-k 索引去取主 KV（主 KV 亦在主机内存，Qwen/GLM 支持跨请求共享前缀主 KV）。整个流程不改模型权重，kernel 结构与 batch 形状固定，因此可以放进 CUDA graph 捕获，避免 CPU 侧调度开销与图重捕获。

Result: 1M token 现代 GPU 上：可同时驻留的请求数为仅做 KV offloading 基线的 1.78×（Qwen）、1.62×（V4.1）、3.03×（GLM-5.2）；当主机内存带宽/容量不构成瓶颈时，解码吞吐为 1.44×/1.25×/2.54×。精度方面，benchmark 平均分相对基线最多下降 3.1%，说明两级索引 + 候选放大基本保住了原始 top-k 选择质量。每个请求保留独立索引，Qwen 与 GLM 请求共享前缀主 KV。

Conclusion: 论文把长上下文稀疏注意力服务的瓶颈定位从"主 KV"转移到"indexer cache"，并给出一个不改模型、可图捕获的两级索引方案：HBM 放压缩索引、主机放全量索引、用候选放大换取召回、由原 indexer 做精排。工程意义在于：在 KV offloading 架构上叠加 Twindex 能近似免费地提升并发与吞吐，且与 CUDA graph、前缀共享等现有服务优化正交组合。遗留问题包括 3.1% 的精度损失边界、主机内存带宽成为新的关键资源、候选放大比例 k'/k 与压缩率需要按模型调参，以及跨请求共享分量在多租户/隐私隔离下的适用性。

Abstract: In long-context decoding, GPU memory (HBM) caps how many requests a GPU decodes at once. Sparse-attention models such as Qwen3.8-Flash-Next, DeepSeek V4.1-Flash and GLM-5.2 add an indexer: at every step it scores all past index entries with its own indexer cache, and attention reads the main KV of only the top-k entries. We find that once serving systems move the main KV to host memory, the indexer cache becomes the HBM bottleneck, at 63% of per-request HBM on Qwen and 75% on V4.1 at 1M tokens. Therefore, we introduce Twindex, which keeps only a compact copy of the indexer cache in HBM and the full indexer cache in host memory. At each step, the copy selects a larger candidate set, and the model's own indexer picks the top-k from the original rows of the candidates in host memory. The copy combines the shared component with the compressed residuals, both learned once offline. Twindex changes no model weights and runs inside CUDA graphs. At 1M tokens on modern GPUs, Twindex fits $1.78\times$, $1.62\times$ and $3.03\times$ as many requests as KV offloading alone on Qwen, V4.1 and GLM-5.2, and reaches $1.44\times$, $1.25\times$ and $2.54\times$ decode throughput when host memory does not limit the batch. Every request keeps its own index, and Qwen and GLM requests share prefix main KV in host memory. In our evaluations, mean benchmark scores are at most 3.1% below the baseline's.

### [2] [Berth: SLO-Preserving GPU Sharing Without New Preemption](https://arxiv.org/abs/2611.25091)
*Mohammadali Khodabandehlou,Mahdi Alizadeh,Lei Gao,Murali Annavaram,Bhaskar Krishnamachari*

Main category: cs.DC

TL;DR: Berth 是一个纯用户态系统，不改内核、驱动、框架或应用，只通过在外部控制 best-effort（如训练）作业"喂给"GPU 的节奏，利用商用 GPU 自带的时间片抢占机制，把闲置的推理预留容量安全地填满 best-effort 工作，同时保住延迟 SLO。


<details>
  <summary>Details</summary>
Motivation: 推理服务按最坏负载预留 GPU，导致大量容量闲置；用 best-effort 作业（训练）填充是显然的解法，但在共享 GPU 上，毫秒级时延的请求会撞上 best-effort 的 kernel 正在运行或排在前面。空间共享无法驱逐、时间共享只给请求"自己的那一轮"、硬件分区靠闲置未用资源来保护 SLO。已有能同时保住 SLO 与利用率的系统要么改 kernel、打驱动补丁、插桩框架——在闭源 GPU 栈上运维方做不到。

Method: 核心观察：商用 GPU 内建的时间切片器已能在亚毫秒内抢占运行中的 kernel，并在 context 无活可干时立即切换；它缺的只是"优先级"，而优先级可以从外部通过控制 best-effort context 有什么可跑的人为构造出来。Berth 的三个机制：(1) feed control——预加载 shim 只在没有请求需要 GPU 时才向 best-effort 作业供应工作；(2) declared deadline reference——把该规则扩展到连续批处理的 LLM 引擎，用声明的 deadline 参考点界定何时可以放手跑 best-effort；(3) 无特权缩短 best-effort 时间片——限定单个长 kernel 可能带来的延迟代价上限。

Result: 在 31 个场景点（采用 MLPerf SLO）上与 13 个基线对比：Berth 的 SLO 达成情况与独占运行相差仅几个百分点，优于所有基线，且 best-effort 吞吐是最强基线的 2.7-3.5 倍；在 LLM 服务旁侧同时训练时，几乎每个请求都能满足 per-token 目标。

Conclusion: 在闭源 GPU 栈上做 SLO 约束下的共享不需要新的抢占机制，只需控制既有抢占机制"看到"的工作量。这为运维方提供了一条零侵入、可部署的利用率提升路径（推理集群填充训练/离线作业），代价是把调度语义从"抢占"转为"供给侧限流"。

Abstract: Inference services keep GPUs reserved for their worst-case load, and most of that capacity sits idle. Filling it with best-effort work such as training is the obvious remedy, and latency is why it rarely happens: on a shared GPU, a request that must finish within milliseconds finds the best-effort job's kernels running or queued ahead of it. Spatial sharing cannot evict them, temporal sharing gives the request only its turn, and hardware partitioning protects it by idling what it does not use. Systems that keep both the SLO and the utilization have reached inside the stack (rewriting kernels, patching the driver, instrumenting the framework), which the operator of a closed GPU stack cannot do. This paper argues that reaching inside is unnecessary. The time-slicer built into commodity GPUs already preempts a running kernel within a fraction of a millisecond and switches the moment a context runs out of work; what it lacks is priority, and priority can be created from outside by controlling what the best-effort context has to run. Berth is a user-space system built on this observation: a preloaded shim feeds the best-effort job to the GPU only when no request needs it (feed control), a declared deadline reference extends the rule to continuous-batching LLM engines, and a shortened best-effort time slice, set without privileges, bounds what a long kernel can cost. Berth changes no application, framework, kernel or driver. Across 31 scenario points with MLPerf SLOs and 13 baselines, Berth meets SLOs within a few percentage points of running alone, above every baseline, with 2.7-3.5x the best-effort throughput of the strongest ones; beside LLM serving, it meets per-token targets for nearly every request while training keeps running. Sharing a closed GPU under SLOs needs no new preemption mechanism, only control over what the existing one sees.

<details>
  <summary>Details</summary>
Motivation: Agent 工作负载在「推理—工具执行」之间交替，上下文不断增长并被反复复用；高并发下 KV 工作集可达数百 GiB，远超 GPU 显存。现有分层 KV 方案把空闲块逐出到 DRAM/SSD，但 agent 返回时必须沿关键路径重新取回，造成推理停顿和 TTFT 尾部时延恶化。核心机会在于：agent 下一步需要的 KV 块内容是可提前确定的，不确定的只是复用时刻——而工具执行时长恰好提供了可预测的时间窗口。

Method: 1) 三级存储层次：GPU HBM → host DRAM → SSD，扩展 vLLM 式 PagedAttention 块管理器；2) tool-aware 时延预测器：为每个工具调用（按工具类型/历史分布）估计完成耗时，据此在工具执行期间把所需 KV 块从 SSD 预取到 DRAM；3) 预取目标限定为 DRAM 而非 GPU，避免预留紧张显存、干扰并发推理请求；4) 去冗余：对仍驻留 GPU 的块不在 DRAM 中保存重复副本，释放 DRAM 容量给预取；5) victim cache 机制：块从显存被逐出时在 DRAM 中保留"受害者缓存"位，使其被逐出后仍可低成本回填而非回源 SSD。

Result: 在 data agent、web agent、coding agent 三类负载上：需要关键路径 SSD 读取的请求占比由 45–76% 降至 10% 以下；相比扩展了 DRAM 与 SSD KV 层的 vLLM，P95 TTFT 最高降低 49%；相比近期 agent-aware 系统，P95 TTFT 降低 1.5–7×。

Conclusion: 该工作表明 agent 负载的 KV 复用具有"内容已知、时刻可估"的结构性特征，把工具执行期当作天然的预取窗口，比盲目 LRU 分层或占用 GPU 显存的预取更划算。工程上，三级 KV 分层 + 时延预测预取有望成为 agent serving 栈（vLLM/SGLang 等）的标准组件；后续值得关注预测误差的鲁棒性、DRAM 带宽与 SSD 带宽之间的争用、多租户公平性，以及在更大规模集群上的可扩展性。

Abstract: LLM agents alternate between inference and tool execution, repeatedly reusing their growing context across calls. Under high concurrency, their combined key-value (KV) cache working set can reach hundreds of GiB, far exceeding GPU memory capacity. As idle KV cache blocks are evicted to slower storage tiers, returning agents incur expensive retrievals that stall inference.
  To address this problem, we present \emph{TripleKV}, a three-tier KV cache management system that hides the delays of these retrievals. %exploits tool execution to hide these delays. In agentic workloads, the KV blocks needed by the next inference request are known in advance; only the time of their reuse is uncertain. TripleKV uses a tool-aware latency predictor to estimate when each tool call will complete and prefetches the required KV blocks from SSD into host DRAM ahead of time. To further improve DRAM utilization, TripleKV eliminates duplication of GPU-resident blocks in DRAM, and introduces a victim-cache mechanism that refills blocks from SSD upon their eviction from GPU memory.
  Across data, web, and coding agents, TripleKV reduces the fraction of requests requiring critical-path SSD reads from 45--76\% to under 10\%. It also reduces P95 time to first token (TTFT) by up to 49\% compared with vLLM extended with DRAM and SSD KV-cache tiers, and achieves 1.5-7$\times$ lower P95 TTFT than recent agent-aware systems.
