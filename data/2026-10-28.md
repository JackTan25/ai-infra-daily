### [1] [INC-MoE: Overlapping In-Network Collectives and Expert Computation for Expert-Parallel Mixture-of-Experts Inference](https://arxiv.org/abs/2610.36339)
*John Stephan,Razvan Puscasu,Xu Yong,Ding Jiutao,Guan Zixuan*

Main category: cs.DC

TL;DR: INC-MoE 把专家并行 MoE 层的 dispatch（AllGather）和 combine（ReduceScatter）卸载到交换机，利用交换机多播与归约实现网内集合通信，并在单个 persistent kernel 内用专用线程块做 AllGather–FFN–ReduceScatter 三阶段流水，使两个方向相反的集合通信与专家计算三者重叠。4 节点 4 路 EP 下 TTFT 最多降 33%、吞吐最多升 50%，与 vLLM 默认路径输出一致。


<details>
  <summary>Details</summary>
Motivation: 多节点 EP 部署中，dispatch（token 送往承载所选专家的加速器）与 combine（专家输出送回 token 所属 rank）都在关键路径上，可主导 MoE 层时延。传统 ring-based 集合通信把两者串行执行，且各自独占链路单向带宽，导致带宽利用不足与通信时间不可隐藏。

Method: 1) 将 dispatch 映射为网内 AllGather（交换机侧多播），combine 映射为网内 ReduceScatter（交换机侧归约），端主机与交换机之间采用 message 语义而非传统集合原语；2) 由于两者使用链路相反方向，并发执行可把带宽受限通信时间相对并发 ring 集合降低 (N-2)/(2(N-1))（4 rank 为 33%，8 rank 为 43%）；3) 在单 persistent kernel 内按 token band 流水：角色专用 thread block 分别执行下一 band 的 gather、当前 band 的 FFN、上一 band 的 reduce，用 device-side 同步实现三重重叠；4) 以 vLLM MoE 层 drop-in 替换方式集成。

Result: 在模拟 4 节点 scale-out、并用专用加速器模拟 INC 交换机的环境中，OLMoE prefill、4 路 EP 下：相对 vLLM 默认集合通信路径，TTFT 最多降低 33%，吞吐最多提升 50%，且输出与基线一致。

Conclusion: 论文给出了一个端到端的系统论证：把 MoE 的 dispatch/combine 下沉到网络交换机，并以 band 级流水让双向集合通信与专家计算重叠，可以显著改善 EP MoE 推理的关键路径。工程影响在于为 INC 交换机提供了明确的使用场景与接口抽象（message 语义、AllGather/ReduceScatter 原语），并展示了与现有服务栈（vLLM）低侵入集成的可行性；局限在于实验基于模拟交换机与 4 节点规模，真实 INC 硬件、更大规模与 decode 场景下的收益仍需验证。

Abstract: In expert-parallel mixture-of-experts (MoE) serving, dispatch moves tokens to the accelerators hosting their selected experts, and combine returns expert outputs to each token's owner. Both operations lie on the critical path and can dominate MoE layer latency in multi-node deployments. We present INC-MoE, an expert-parallel MoE layer that offloads dispatch and combine to the network switch and overlaps both collectives with each other and with expert computation. Dispatch uses in-network AllGather through switch-side multicast, while combine uses in-network ReduceScatter through switch-side reduction. Both collectives use message semantics between the end hosts and the switch. Because the in-network collectives load opposite directions of each link, executing them concurrently reduces bandwidth-bound communication time by $(N-2)/(2(N-1))$ relative to concurrent ring-based collectives: 33% for four ranks and 43% for eight.
  INC-MoE partitions tokens into bands and processes them through a three-stage AllGather-feed-forward network (FFN)-ReduceScatter pipeline inside a single persistent kernel. At steady state, role-specialized thread blocks gather the next band, compute the current band, and reduce the previous band concurrently, overlapping both collectives with each other and with computation using device-side synchronization. INC-MoE integrates as a drop-in replacement for the MoE layer of vLLM. We evaluate it in an emulated four-node scale-out deployment with a dedicated accelerator emulating an in-network computing (INC) switch. On OLMoE prefill with four-way expert parallelism, INC-MoE reduces time to first token (TTFT) by up to 33% and increases throughput by up to 50% relative to vLLM's default collective path, while matching its outputs.

### [2] [IOSage: Detecting HPC I/O Bottleneck Patterns to Guide LLM Recommendations](https://arxiv.org/abs/2610.36370)
*Mahdi Banisharif,Tabassum Mahmud,Ahmad Tarraf,Suren Byna,Ali Jannesari*

Main category: cs.DC

TL;DR: IOSage 是一个 I/O 性能诊断系统：用监督式分类器（在大量已标注 Darshan 日志上训练）而非 LLM 来判定日志中存在哪些 I/O 瓶颈模式，再把分类器输出的瓶颈模式、作业配置文件、逐文件 Darshan 证据以及由基准训练运行构建的"模式卡片"（pattern card）一起交给 LLM，由 LLM 生成具体的修改建议。人工施加建议后实测：openPMD kernel 中位总墙钟时间加速 4.38x（另一存储层级 4.02x），WRF 逐小时 restart 加速 1.42x。分类器在 488 条标注测试日志上 Micro-F1 0.929（OOD 158 条上 0.832），显著优于 Drishti 规则、WisIO 和去掉文献检索的 IOAgent 流水线；在 TraceBench 生产 trace 上精度最高（0.82）。

  <summary>Details</summary>
Motivation: HPC 应用常大量浪费并行文件系统带宽，但把 Darshan 日志变成可执行的 I/O 修复方案仍依赖稀缺的 I/O 专家。规则类工具靠专家设定阈值做计数比对，泛化差；基于 LLM 的工具（ION、IOAgent）让 LLM 直接判断日志里存在哪些瓶颈——但单条日志不提供"什么是异常"的基线，LLM 缺乏参照，容易对健康作业也编造问题和建议。作者的核心论点：瓶颈判定应由有标注基线支撑的分类器完成，LLM 只负责把已确认的瓶颈翻译成针对性修改方案，二者职责分离。

Method: 1) 在大量已标注 Darshan 日志上训练多标签分类器，识别已登记的 I/O 瓶颈模式，并同时作为"门控"（gate）判断该作业是否存在值得报告的瓶颈；2) LLM 的上下文由四部分组成：分类器检出的模式、作业配置文件、逐文件 Darshan 证据、以及每个模式对应的 pattern card（由基准训练运行构造，给出该模式的特征与已验证的修复方向）；3) LLM 输出具体修改建议，由人工作业后测量；4) 评测含 488 条标注 benchmark 测试（其中 158 条来自训练外的配置与作业）、78 条无模式运行（测误报/门控）、6 个应用场景（openPMD、WRF restart 等），以及 TraceBench 的 9 条生产 trace；对比 Drishti 规则、WisIO、IOAgent 流水线（含去掉其文献检索模块的消融），并以 Claude Sonnet 4 / GPT-4o / Llama 3.1 三种 LLM 交叉验证、采用重复配对运行降低噪声。

Conclusion: IOSage 的主要系统贡献是把 I/O 诊断中的"发现瓶颈"与"生成修复"两个环节解耦：由有标注数据支撑的分类器负责判定与门控，由 LLM 负责模式到代码改动的翻译，并用 pattern card 注入基准运行的可验证证据。这一设计同时改善了三项工程指标——建议的可执行性与实测加速、跨 LLM 后端的一致性、以及在无异常场景下的大幅误报抑制——并在 benchmark 与生产 trace 上均胜过规则工具和纯 LLM 流水线。工程含义：对 Darshan 类监控数据的自动化调优，应把 LLM 放在受限的"建议生成"位置而非"异常判定"位置；其效果上限受分类器模式覆盖度约束（仅覆盖已登记模式，长尾与新瓶颈仍需专家），且端到端收益依赖建议被人工实际落地，尚未形成闭环自动调优。

Abstract: HPC applications often leave much of their parallel file system's bandwidth unused, and turning their Darshan logs into concrete I/O fixes still requires a scarce I/O expert. Rule-based tools flag counters against thresholds set by experts, and in tools built on large language models (LLMs), such as ION and IOAgent, the LLM decides which bottlenecks a log contains. We present IOSage, in which a classifier trained on many labeled logs, not the LLM, makes that decision, since a single log gives an LLM no baseline for what is abnormal. The LLM receives the I/O bottleneck patterns the classifier detects, the job's configuration files, per-file Darshan evidence, and for each pattern a card built from benchmark training runs, and writes recommended changes. Applied by hand and measured in repeated paired runs, the changes IOSage names speed up median total wall time 4.38x for an openPMD kernel (4.02x on a second storage tier) and 1.42x for hourly WRF restarts. For 5 of the 6 application scenarios with a helpful change, IOSage with Claude Sonnet 4 names it, including the change for 10-minute WRF restarts (up to 1.93x faster); with GPT-4o and Llama 3.1 as well, the classifier and cards name more helpful changes than the LLM alone. On 78 benchmark test runs without a pattern, the LLM deciding alone proposes changes for 64; with the classifier, for 9. The classifier reaches 0.929 Micro-F1 on 488 labeled benchmark test runs (0.916 as the gate; 0.832 on the 158 from configurations and jobs outside training), above Drishti's rules, WisIO, and IOAgent's pipeline without its literature retrieval. On TraceBench's nine expert-labeled traces from production systems, it has the highest precision of the tools compared (0.82), with 2 false positives against 12 for the keyword-mapped LLM diagnoses shipped with TraceBench and 5 for Drishti, on the five issue labels that match registered patterns.

*Yaojian Chen,Dazhi Peng,Zhui Zhu,Leshan Li,Haojun Sun,Yiyun Zheng,Qingfeng He,Shangzhan Li,Xianglong Deng,Yifei Shen,Shengye Xiang,Zhen Li,Lin Gan,Yuxuan Li,Xu Han,Zhiyuan Liu*

Main category: cs.DC

TL;DR: 论文提出 JustGoal，一个"仅目标（goal-only）"的通用智能体基线：只给通用 agent 优化目标和约束，不提供 kernel 领域知识库、专用评测基础设施或预定义搜索工作流，由 agent 自行构建评测循环来生成并优化 GPU kernel。在 B200 上，JustGoal 在 10 个算子中的 8 个超过开源库，单算子几何平均加速 1.14x–2.34x；在有公开对比的 9 个算子中，5 个超过最快的公开专用 agent kernel。同模型控制实验显示专用 harness（KDA-0.5）仅达 JustGoal 的 0.95x，单机制消融中领域知识与预定义工作流均无稳定收益。


<details>
  <summary>Details</summary>

Abstract: A small number of GPU kernels often determines the efficiency of large language model training and inference. High-performance kernel development typically relies on expert knowledge through manual implementation, collaboration with general-purpose models, or specialized agents equipped with domain knowledge, evaluation methods, and search workflows. We investigate how much value this knowledge provides as foundation models become stronger. These results indicate that specialized machinery should be justified by clear gains over a same-model, same-scope goal-only baseline and reevaluated whenever the foundation model changes.

### [4] [Agar: What-If Analysis for Microservice Applications](https://arxiv.org/abs/2610.36636)

<details>
  <summary>Details</summary>
