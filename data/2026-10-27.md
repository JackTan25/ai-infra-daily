### [1] [LooseLeaf: Enabling Serverless GPUs for Computational Notebooks](https://arxiv.org/abs/2610.33275)
*Yusen Wu,Tingfeng Lan,Benjamin Carver,Haoliang Wang,Geoffrey Fox,Yue Cheng*

Main category: cs.DC

TL;DR: LooseLeaf 将 serverless GPU 执行引入交互式 notebook：通过静态分析推导每个 cell 的 state closure（最小变量集）与 import closure（最小依赖包集），在用户编辑 cell 的窗口期内预热 GPU worker，执行后数秒内持久化更新后的状态，从而在每次 cell 执行后即可回收 GPU，同时保持"钉住会话"级别的交互体验。


<details>
  <summary>Details</summary>
Motivation: Notebook 传统上为整个 session 独占一块 GPU，但 GPU 仅在 cell 执行期间真正计算，其余时间（用户思考、编辑、调试）完全空闲，造成严重的资源浪费和 GPU-hour 成本。直接的 serverless 化会带来一个核心矛盾：每个 GPU cell 都需要在全新 worker 上重建累积的 notebook 状态（变量 + 已导入包），这一重建开销随 notebook 推进不断增长，会淹没 serverless 带来的弹性收益。因此关键问题是：能否让状态重建足够便宜，使"每 cell 后回收 GPU"在经济与延迟上都成立。

Method: 1) 静态分析 notebook：由 cell 代码推导 state closure（该 cell 实际用到的最小变量集合）与 import closure（最小包依赖集合）；2) 关键观察与验证：在 5,000 个真实 notebook 上统计这些闭包规模，证明其足够小；3) 机会利用：用户编辑 cell 的间隙提供了数秒的提前量，LooseLeaf 在该窗口内并行地按 closure 准备（冷启动/预热）GPU worker，将冷启动延迟隐藏在人机交互时间中；4) 执行结束后在数秒内 checkpoint 更新后的状态，保证 worker 可立即回收，实现 per-cell 粒度的 GPU 复用与释放。

Result: 95–98% 的 GPU cell 启动无可感知延迟；交互性与钉住式会话持平；相比 SOTA notebook 平台减少 32–55% 的 GPU-hour 消耗。闭包分析在 5,000 个真实 notebook 上验证了闭包规模较小、且编辑窗口内足以完成准备。

Conclusion: LooseLeaf 的贡献在于把"状态重建成本"从不可承受变为可隐藏：用 closure 分析将全量状态恢复降维为最小必要状态，再借人机交互的天然空闲窗口做预热，从而在 notebook 这一延迟敏感场景中实现 serverless GPU 的按 cell 计费。工程影响上，它给出一条通用范式——以程序分析驱动的按需状态物化 + 交互间隙隐藏冷启动，可推广到交互式训练/调试、多租户 notebook 平台与 GPU 资源池的弹性调度，同时把性能指标从"启动延迟"扩展到"启动延迟 + 状态恢复 + checkpoint 开销"的端到端代价模型。

Abstract: Computational notebooks reserve a GPU for the whole session, yet the GPU computes only while a cell executes and sits idle otherwise. Serverless execution would release the GPU between cells, but reconstructing the accumulated notebook state on a fresh worker imposes substantial cost on every GPU cell. This paper presents LooseLeaf, a serverless GPU platform for interactive notebooks. LooseLeaf derives the state and import closures of each cell, the minimal variables and packages that the cell needs. Our analysis on 5,000 real-world notebooks shows that these closures are small, and user-cell editing leaves seconds to prepare them. LooseLeaf prepares a GPU worker with these closures while the user edits the cell. After execution, the worker saves the updated state within seconds, so the GPU is reclaimable after every cell. LooseLeaf starts 95-98% of GPU cells with no visible delay, matches the interactivity of a pinned session, and provisions 32-55% fewer GPU-hours than state-of-the-art notebook platforms.

### [3] [DualPace: Decoupled Scheduling and Cooperative GPU--CPU Decoding for LLM Serving](https://arxiv.org/abs/2610.33501)
*YuXuan Lin,KeQiang Wu,Kingsum Chow*

Main category: cs.DC

<details>
  <summary>Details</summary>
Motivation: LLM serving 依赖 batching 提升吞吐，但 KV cache 随序列长度增长，限制了 GPU 常驻并发度。CPU offloading 可用 host memory 扩展 KV 容量，然而现有系统是「GPU-gated」的：CPU-resident 请求只在 GPU 调度器恰好给出重叠机会时才推进，host memory 与 CPU 算力无法作为独立服务资源被利用，导致 CPU 侧进展突发化、负载下 ITL 尾部时延被放大。

Method: 核心是把调度权拆分到两个引擎：(1) GPU engine 执行 prefill 与 GPU-resident decode；(2) 基于 AMX 的 CPU engine 独立地对 CPU-resident decode 进行 batching 和推进。两引擎调度解耦但执行协同——CPU 可本地完成一次完整 decode 迭代，也可对 dense 阶段选择性调用 GPU Dense Assist（把合适的部分卸载回 GPU 以提高效率），避免 CPU 成为新瓶颈。硬件特异的 batch size 与路由决策（哪些请求/哪些阶段走 CPU 还是 GPU）由离线 profiling 生成的配置指导。

Result: 在 decode 为主的场景下，DualPace 相对 SOTA 开源 CPU-offloading 系统 NEO 提升吞吐 6.9–43.2%，相对 vLLM 提升 11.5–90.6%，同时维持同等延迟水平；并保留 NEO 相对 vLLM 的 P99 TTFT 优势，在相同 P99 ITL 水平下可支撑比 NEO 高 7.3–50.5% 的请求速率。

Abstract: Large language model (LLM) serving relies on batching to improve inference throughput, but the key-value (KV) cache grows with sequence length and limits GPU-resident concurrency. CPU offloading can expand KV capacity using host memory, yet existing systems remain largely GPU-gated: CPU-resident requests make progress only when the GPU scheduler exposes suitable overlap opportunities. As a result, host memory and CPU compute cannot act as an independent serving resource, leading to bursty CPU-side progress and inflated tail inter-token latency (ITL) under load.

DualPace separates scheduling authority across two engines: the GPU engine executes prefills and GPU-resident decodes, while an AMX-enabled CPU engine independently batches and advances CPU-resident decodes. The engines are decoupled in scheduling but cooperative in execution: the CPU can execute a complete decode iteration locally or selectively invoke GPU Dense Assist for dense stages, while offline profiles guide hardware-specific batching and routing.

DualPace also preserves NEO's P99 time-to-first-token (TTFT) advantage over vLLM while sustaining 7.3--50.5\% higher request rates than NEO at the same level of P99 ITL.
