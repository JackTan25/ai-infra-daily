### [1] [Conditional Work Bounds and Timing Evidence for an Industrial NDT Scan Matcher: Cross-Language Work-Trace Conformance](https://arxiv.org/abs/2611.33159)

### [2] [Same Seed, Different Top Prediction: Cross-Platform Reproducibility of AlphaFold 3 Inference on TPUs, GPUs, and CPUs](https://arxiv.org/abs/2611.34462)
*Lorenzo Pazienza*

Main category: cs.DC

TL;DR: 该论文研究了AlphaFold 3 (AF3) 的数值可复现性问题：由于AF3每台设备独立计算并返回采样结构中的最高分结构，不同硬件（TPU代际、NVIDIA GPU、CPU）之间的浮点差异会导致相同输入与种子返回不同的预测结构，且AF3文档与输出均未对此警示。作者跨5类加速器+CPU系统测量了这一效应，并给出修复建议。


<details>
  <summary>Details</summary>
Motivation: AF3 的推理管线是"采样多个结构—按置信度排序—返回 top-1"，且无跨设备一致性保证。实际部署中，计算中心可能将任务调度到不同GPU型号甚至CPU节点上，用户在同一输入/种子下会得到不同结果而没有任何告警。这对以AF3输出做下游科学结论、以及构建可复现的推理服务/流水线都是隐患。论文旨在量化该风险、指出根因，并给出低成本的一致性方案。

Method: 受控跨设备实验：固定输入、权重、随机种子与全部超参，在两种 Google TPU（v5e、v6e）、三款 NVIDIA GPU（L4、A100、H100）和 Intel Xeon CPU 上运行。主实验为 60 个蛋白-配体复合物 × 5 个种子（共 300 次预测），统计 top-1 结构发生变化的频率；另外对比"重新编译"（recompilation）的影响以分离编译器不确定性与硬件浮点不确定性；并在 72 个新靶点上做复现验证，补充 TPU↔CPU、A100↔H100 的对照。进一步通过分析接近并列（near-tied）的候选样本定位机制，并尝试用 float32 trunk + 全精度矩阵乘（不使用低精度/张量核降精度路径）来消除差异。

Result: 主实验：仅切换 TPU 代际（v5e→v6e）就使 18.0% (54/300) 的预测 top-1 结构发生改变；重新编译在两种 TPU 上从未改变结果，但在 L4 GPU 上造成 7.3% 变化。结构本身几乎不动，但 top-1 姿态在"正确↔错误"间翻转的比例为 3.3%–3.7%，而换一个种子约为 10%——即设备噪声约为换种子的 1/3 量级。这些翻转几乎总来自同一个有效性检查（配体距离在 2 Å 内）。在 72 个新靶点以及 TPU↔CPU 上复现了该效应；A100↔H100 的差异甚至大于重编译带来的差异，尽管开发者已在这两款 GPU 上验证过数值精度。探索性分析将该效应关联到 near-tied 候选。采用 float32 trunk 与全精度矩阵乘后，五类加速器在几乎全部预测上达成一致。

Conclusion: AF3 的 top-1 输出不具备跨设备可复现性，且现有文档与输出格式均未暴露这一不确定性；差异在结构层面很小，但在离散的排名/clash 判定上会被放大为正确性翻转。建议：(1) 报告中注明所用设备；(2) 公开所有 near-tied 采样结构而非仅 top-1；(3) 需要设备无关结果时使用 float32 trunk 与全精度矩阵乘（以性能换一致性）。对系统的启示是，对"采样+排序"型推理服务，应在服务层记录硬件指纹、显式标记低裕度（low-margin）样本，并把"降低精度提升吞吐"的默认策略与科学可复现性要求显式权衡。

Floating-point results can differ between devices, so the same input and seed may return another structure. Neither AlphaFold 3's documentation nor its outputs warn of this. We measure how often the device changes the returned structure, and tell users what to report and how to make devices agree. We used identical inputs, weights, seeds, and settings on two Google tensor processing unit (TPU) generations (v5e, v6e), three NVIDIA GPUs (L4, A100, H100), and an Intel Xeon CPU. On 60 protein-ligand complexes, with five seeds each, switching TPU generations changed the top-ranked sample in 18.0% of 300 predictions. Recompiling never changed it on either TPU, but did so in 7.3% on the L4 GPU. Yet the structures barely moved. The top-ranked pose switched between correct and incorrect in 3.3% to 3.7% of predictions, against about 10% for a new seed. These switches nearly always came from one validity check, with the ligand within 2 angstroms. Follow-ups found the effect again on 72 new targets and between the TPUs and the CPU. Between the A100 and H100 it exceeded recompilation, although AlphaFold 3's developers verified its numerical accuracy on both. An exploratory analysis links the changes to near-tied candidates. We recommend reporting the device and every near-tied sample. A float32 trunk with full-precision matrix products made all five accelerators agree on nearly every prediction.

### [3] [RankCast: Phase-Aware Rank Balancing in MoE Serving](https://arxiv.org/abs/2611.33542)
*Kaidi Fu,Xu-Hao Lu,Pingwei Sun,Jianchao Tan,Yuchen Xie,Xunliang Cai*

Main category: cs.DC

TL;DR: RankCast 在 PD 分离 + EP 的大规模 MoE 服务中，通过在每个 token 的 Top-L 候选专家集合内重排 Top-k 分配（L>k），统一地把 Prefill 阶段"最忙 rank 的最大 token 数"和 Decode 阶段"跨 rank 最大活跃专家数"降下来，并在 SGLang 与 DeepEP 上落地实现。


<details>
  <summary>Details</summary>
Motivation: MoE 的 EP 并行需要每层等待最忙 rank（straggler），造成 rank 级负载不均衡。作者指出 P 与 D 的瓶颈来源不同：Prefill 是 compute-bound，延迟由最忙 rank 的最大 token 数决定；Decode 在中等 batch 下是 memory-bound，延迟由跨 rank 的最大 active-expert 数决定（因为需要按专家加载/访问权重，专家数决定访存与 kernel 启动开销）。因此已有的单一维度负载均衡方案无法同时覆盖两阶段，需要一个统一框架同时压低这两个 rank-level 最大值。

Method: 核心是"受约束的专家分配重映射"：对每个 token 保留路由预测的 Top-p 专家不变，剩余 k−p 个名额从其 Top-L 候选（L>k）中挑选，从而在不改变每 token 专家数的前提下获得分配自由度。Prefill 路径：为每个 rank 计算一个"价格"（price per rank），用价格信号引导灵活的那部分分配流向负载较低的 rank，从而削减最忙 rank 的 token 计数。Decode 路径：在最忙 rank 上关闭（不分配）部分专家，同时满足每个 token 的约束，从而降低跨 rank 的 max active-expert 数。工程实现上集成进 SGLang 与 DeepEP，将 RankCast 的 kernel 与模型执行重叠（overlap），并复用 DeepEP 已有的通信通道传输元数据，避免额外通信开销。

Result: 在 Qwen3-235B-A22B（EP=8）与 Qwen3.5-397B-A17B（EP=16）上：消除最忙 rank 超过 75% 的额外 Prefill 负载；Prefill 输入吞吐最高提升 19%；每输出 token 的 Decode 时间最多下降 10%；质量损失低于 1 个百分点。

Conclusion: RankCast 表明，MoE EP 服务的负载均衡应区分 P/D 的不同瓶颈指标（token 数 vs 活跃专家数），而 token 级 Top-L 候选内的灵活重分配是一个代价极低（<1% 质量损失）、无需额外通信的通用手段。其系统贡献在于把算法侧的"轻微路由扰动"与 SGLang/DeepEP 的执行流和通信通道对齐，实现了近零开销的 online 负载整形，对 PD 分离式 MoE 推理的吞吐与 TPOT 都有直接收益。

Abstract: Modern large language model (LLM) inference increasingly adopts disaggregated architectures that separate Prefill (P) and Decode (D) phases. Meanwhile, Expert Parallelism (EP) has been widely adopted in large Mixture-of-Experts (MoE) model serving. However, load imbalance still slows down MoE inference because each layer must wait for the busiest EP rank. The main source of latency differs between prefill and decode. Prefill is compute-bound, and its MoE layers' latency is determined by the maximum token count of the busiest rank. At the same time, under moderate batch sizes, Decode is memory-bound, so the latency is dominated by the maximum active-expert count across ranks. To solve both problems under a unified framework, we present RankCast, a system that reduces rank-level maximum token counts during prefill and active-expert counts during decode. For every token, RankCast preserves the predicted Top-p experts and chooses the remaining k-p from its Top-L candidates (L > k). In prefill, RankCast yields a price per rank that steers flexible assignments to less loaded ranks. In decode, RankCast closes experts on the busiest ranks while preserving the constraints for each token. Both paths are implemented and tested in the state-of-the-art inference frameworks SGLang and DeepEP. We overlap RankCast's kernels with model execution and reuse the existing DeepEP communication channel for metadata transmission. On Qwen3-235B-A22B with EP=8 and Qwen3.5-397B-A17B with EP=16, RankCast removes over 75% of the busiest rank's excess prefill load, improves prefill input throughput by up to 19%, and reduces decode time per output token by up to 10%. The quality cost is below one percentage point.

<details>
  <summary>Details</summary>
Motivation: 现有 PP 引擎把 prefill 切成 token chunk 以限制 decode 停顿，但 chunk size 是一个过度耦合的旋钮：它同时决定 GPU 批宽、阶段间激活传输量、权重重载频率与交互请求的排队延迟。小 chunk 导致权重反复加载、算力利用率低；大 chunk 让 GPU 与链路长时间被占用，长上下文混合负载下的短请求 TTFT 被严重拖长（原生 vLLM 下 p95 TTFT 达 129.8 s）。同时，PCIe 与异构卡的带宽波动与不对称使静态配置不可行。

Large chunks can keep the GPU and the link busy long enough to delay interactive requests.

A fused Triton Hadamard-INT4 codec compresses activations, which travel in independently sized row groups over parallel TCP sockets. The scheduler uses latency slack to choose batch width, slice depth, and row-group size. We evaluated PipeAxes in 97 replays covering 5,016 requests on A800, RTX 4090, and RTX 3090 GPUs. All 74 requests met their latency targets during a tenfold bandwidth swing. In a mixed 64K-context workload, p95 time to first token for short requests fell from 129.8 s with native vLLM to 512 ms.
